# 今後の実装・機能改善の進め方

更新日：2026-10-12。基本機能・UI・追加仕様A1〜A3を実装し、レビューR01〜R09を修正した。**次は対象PCでlive・実紙・ngrok認証を確認し、その後はタグの質と当日の待ち時間を測って改善する。** 根拠は [基本仕様](spec.md)、[追加仕様](SPEC-ADD-1.md)、[UI仕様](UI.md)、[実装レビュー](IMPLEMENTATION-REVIEW.md)。

## 1. 今回整えた基準

| --- | --- | --- |

| 生成 | 旧処理による上書き防止、fetch中止、サーバー全体の同時3件・待機60件・120秒 | liveの待ち時間、複数端末の負荷、混雑時の再開 |

## 2. 改善に移るための確認

本番PCで次の確認を通し、結果と対象コミットを記録する。

1. `npm run verify` が成功する。今回の環境では本番ビルドも成功したが、対象PCの設定でも確認する。
2. 基本仕様の受け入れ確認1〜9をmockで通す。375pxの公開トップ、1280×720の発表画面、保存→消去→復元、生成再生、印刷を含める。
3. 追加仕様の受け入れ確認1〜9のMUSTを通す。SHOULDを入れた場合は確認7も通す。従来の参加者のタグが1人追加で変わらず、名前がAPIに入らないことを確認する。
4. 学内/VPNのPCで `npm run llm:check`、ダミー15・40・200人のlive生成を確認する。接続できない場合に参加者が増えず、手入力が残ることも確認する。
5. [ngrok手順書](NGROK.md) に従い、未認証・許可外・許可された利用者で画面とAPIを確認する。

2026-10-12、この作業環境で `ui`（`fadb1fc`）の検証用コピーを使い、1〜3のモックでの機能確認を実施した。verify（98テスト・本番ビルドを含む）と基本・追加仕様の18手順は成功。印刷はChromiumのPDF出力で確認し、印刷ダイアログ自体・実紙・別の本番PCの環境差は未確認。対象と各項目の証拠は [受け入れ確認結果](ACCEPTANCE-2026-10-12.md) に記録した。

実回答、APIキー、実回答を含むバックアップをAIに渡さない。再現には同じ構造の架空データを使い、エラー報告もキー・回答を伏せる。

## 3. 改善候補は効果と確認方法を決めてから着手する

| 優先 | 改善候補 | 最初に測ること | 改善後の判断基準 |
| --- | --- | --- | --- |
| 高 | 個性タグの自然さ、回答からの根拠、共有タグの納得感 | 固定のダミー40人で、運営が直したタグ数と不自然な例を記録 | 人の修正が減り、回答にない断定やNG語が増えない |
| 高 | 当日の1人追加の待ち時間 | モデル別のextract・rank時間、合計時間、失敗数 | 追加仕様の目安30秒以内を狙い、既存の人のタグを維持 |
| 高 | 飛び入り参加だけの印刷と使いかけ用紙 | 入力から配布までの時間、紙の消費、位置ずれ | 印刷対象と開始段が分かり、1人でも正しいラベル位置で刷れる |
| 中 | 初めて使う職員の迷いを減らす | 説明なしで「読み込み→生成→修正→印刷」してもらい、止まった場所を記録 | 停止箇所が減り、次の操作を自分で選べる |
| 中 | 接続エラーと再開の分かりやすさ | 通信切断、混雑、キー不正で表示と復旧手順を確認 | 原因に合った案内が出て、作業データを保ったまま復旧できる |
| 中 | 40〜200人での処理時間・偏り | 所要時間、要確認人数、共有タグの最大人数、仲間の最小人数、遭遇率 | 下限とタグの意味を保ちつつ、待ち時間と偏りを改善 |

「遭遇率を上げる」だけを目的にしない。無関係な人に同じタグを配ると数値だけは上がるため、回答との関係と人の評価も一緒に見る。

共有編集、参加者向けスマホフォーム、アカウント別の役割、データベースは現在の仕様の範囲を超える。必要になった時点で目的・保存場所・同期・権限・同意を追加仕様に書く。ngrok認証を付けても、ブラウザ間の同期やアプリ内の役割分担は生まれない。

## 4. モデルとプロンプトの改善方法

同じダミーExcelを使い、同じ条件で現行版と変更版を比較する。モデル、プロンプト、生成パラメータ、UIを一度に変えず、原因が分かる単位で変える。

mockは操作・計算・再開の確認に使う。本物のタグの質や速度はliveで評価する。mockは話題辞書を使うため、mockで良い結果でも実際のおいとまの品質を証明しない。

手元の学内/VPN環境で、例として次を実行する。`.env.local` がliveになっていることを確かめる。

```bash
npm run pipeline -- --file public/samples/sample-40.xlsx --out private/baseline-40.json
```

モデルやプロンプトを1点変えた後、別ファイルに保存する。

```bash
npm run pipeline -- --file public/samples/sample-40.xlsx --out private/candidate-40.json
```

ダミーを使っていても作業データは `private/` に置く。比較には、モデル名、対象コミット、各段階の所要時間、修正したいタグの数、不自然なタグの例、指標を残す。生成には揺れがあるので、採用判断に使うlive条件では複数回確認し、1回だけの良い結果で決めない。

速いモデルへの変更は、速さとタグの意味を両方確認する。抽出・順位のバッチサイズや同時実行数は、1人分の品質が安定してから調整する。現在の同時実行数3は1つのNode.jsサーバー全体で共有する。複数人でliveを実測し、待ち時間とサーバー負荷を見てから調整する。複数サーバーへ増やす場合は共通キューを先に設計する。

## 5. 毎回の作業の型

1. **課題を書く**：誰が、どの操作で、何に困るか。再現用ダミーと、直ったと判断する条件を付ける。
2. **仕様を確定する**：既存の不備なら参照する節とレビューID、新機能なら `docs/SPEC-ADD-2.md` などにMUSTと対象外を書く。見た目を変えるなら `docs/UI.md` も合わせる。
3. **実装を1件に絞る**：基盤・API・文書は `main`、画面操作・表示・印刷は `ui` で作業し、基盤の変更後は `ui` に取り込む。修正、関係する検証、小さな判断の記録を行う。Next.jsのコードを書く前に、インストール済み `node_modules/next/dist/docs/` の該当ガイドを読む。
4. **検証する**：意味のある回帰テストと `npm run verify`、関係するブラウザ手順を通す。印刷は普通紙、本物のおいとまは学内で担当者が確認する。
5. **レビューして保存する**：変更内容、検証結果、未検証事項を記録し、1つの作業単位でコミットする。pushや外部公開は運用手順に従って担当者が行う。
6. **効果を見る**：直した条件と改善の指標を比較し、効果があれば次の課題へ進む。

## 6. AIに依頼する文面の例

タグの質を改善する場合：

```text
AGENTS.md、docs/spec.md、docs/SPEC-ADD-1.md、docs/IMPLEMENTATION-REVIEW.mdを読んでください。
固定のダミー40人で個性タグの表現だけを改善してください。
現在の問題例と修正件数を先に記録し、プロンプトの1点だけを変えて比較してください。
回答にない断定、NG語、要確認人数を増やさず、人の修正件数を減らすことが採用条件です。
既存の共有割り当て・印刷座標・中止処理は維持してください。
Next.jsのコードを書く前に、node_modules/next/dist/docs/の関連ガイドを読んでください。
意味のある回帰テストとnpm run verify、関係するブラウザ操作を確認してください。
小さな判断はdocs/DECISIONS.mdに記録し、比較結果と未検証事項を報告してください。
キーと実データは使わず、pushや公開はしないでください。
```

改善を依頼する場合は、先に「現在の測定結果」「変更する1点」「採用する条件」を渡す。完成条件が曖昧なまま「全体を良くして」と頼むより、変更と効果を比較しやすくなる。
