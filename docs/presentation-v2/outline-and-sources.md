# 構成・必須要素の対応・参照資料

対象：審査員（教授・企業）／開発成果報告／本編4分／16:9。分析した版は 2026-10-15 時点の作業ツリー（HEAD `480d010`）。`.env.local`・実回答・APIキーは読んでいない。

## 1. ソースから確認したこと

**目的と課題**：交流会の名札に「話題シール」（個性タグ1つ＋共有タグ2つ）を足し、肩書き以外の話から会話を始められるようにする。自己紹介を読み解くにはAIが要るが、自己紹介は個人情報なので、学内AIのおいとまで処理する。会話が増えたかどうかは、まだ測っていない。

| コンポーネント | 責務 | 根拠 |
| --- | --- | --- |
| 主催者のブラウザ | Excel解析、生成の指揮（分割・並列・進捗・再開）、割り当てと指標の計算、保存（localStorage）、印刷 | `src/lib/pipeline/run.ts`、`src/lib/assign.ts`、`src/lib/store.ts`、`src/app/admin/*` |
| Next.js サーバー（主催者PC、127.0.0.1） | APIキーの保持、プロンプト組み立て、JSONの取り出し・検証・再試行、同時実行の制限。参加者データは保存しない | `src/app/api/llm/*/route.ts`、`src/lib/llm/{client,tasks,prompts,schemas,limiter}.ts` |
| おいとま（学内LLM、OpenAI互換） | 話題の読み取り（extract）、共有タグ候補（catalog）、当てはまり順（rank）、会場のまとめ（summary）、個性タグの別案（regenerate） | `src/lib/llm/prompts.ts`、`docs/spec.md`「おいとま連携」 |
| シールと印刷 | 1人1行に3枚、A4・24面（66.0×33.9mm）、位置補正 | `src/components/{Sticker,StickerSet,StickerSheet}.tsx`、`src/config/event.ts` |

**主要な流れ**：Forms回答Excel → 取り込み（列の自動判定）→ タグ生成（5段階）→ 主催者の確認・修正 → A4ラベル印刷。生成は ①extract（8人ずつ・同時3）→ ②catalog（全員で1回）→ ③rank（15人ずつ・同時3）→ ④割り当て（コード。2つ持てない人だけ③を再実行）→ ⑤summary（失敗しても続行）。

**設計判断とトレードオフ**：AIは候補と順位まで、割り当てはコード。出力が短く崩れにくい、下限をコードで守れる、失敗した分だけやり直せる。その代わり上限は目安で、付け替え先がなければ超える。採用できるタグが2つ未満になる極端な場合は、全員に2つ持たせることを優先して要確認の印を付ける。

注意して扱った点：

- 仕様書冒頭の「回答は学内から出ない」は、2026-10-14 の ngrok 方針で学外利用時に前提が変わる（`NGROK.md` §7）。そのため9では「学外のAI事業者に渡さない」「AI処理は学内」と表現し、「通信が学外を通らない」とは書いていない。
- 9の「セキュア」は、学内AIでの処理と、アプリ側の最小化（名前を送らない等）を根拠にした設計上の主張。所属は送ること、自由記述中の人名は自動で匿名化しないこと、同意列がないExcelはデモ用に全員同意として扱うことは、ノートに明記した。
- 8の「コードが守る」は、通常の経路で下限未満のタグを外し、補充は人数を増やすだけであることに基づく。採用タグが2つ未満になる極端な場合の例外はノートに書いた。
